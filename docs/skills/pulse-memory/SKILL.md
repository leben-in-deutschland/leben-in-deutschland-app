# PULSE Memory

Keep knowledge that should change future work. Do not use memory as a task log.

## Procedure

1. Identify the exact lesson and the future situation where it matters.
2. Verify the lesson against implementation, tests, incident evidence, or an accepted decision.
3. Search existing `docs/memory/` files to avoid duplication.
4. Define the narrow inverse edit before writing.
5. Add a concise entry to the most specific memory file.
6. Link the feature, ADR, plan, incident, or verified source when useful.
7. Remove or update older memory that the new evidence makes false.
8. Use an ADR instead when the content is an accepted architecture or product decision.
9. Use a plan instead when the content is temporary work state.
10. Validate the final note and links.

Canonical workflow:
<https://github.com/manishtiwari25/pulse/blob/main/docs/workflows/memory-update.md>

## Good Memory

Good memory is brief, specific, sourced, reusable, and easy to delete when it
becomes wrong.
